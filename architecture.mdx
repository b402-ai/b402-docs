b402 is one protocol family with two production implementations. The Solana stack and the EVM stack diverge in how they realize the underlying primitives, but the mental model is the same: a **Protocol Layer** that holds the cryptographic guarantees, a **Service Layer** that bridges HTTP and the chain, and a **Developer Layer** that agents and apps integrate against.

## Protocol Layer

The on-chain primitive on each side.

| Concept             | Solana                                                       | EVM                                                                                  |
|---------------------|--------------------------------------------------------------|---------------------------------------------------------------------------------------|
| Settlement primitive| **Shielded pool program** (`b402-pool`) + Groth16 verifier   | **b402 Relayer contract** (EIP-712 `transferWithAuthorization`)                       |
| Privacy primitive   | Railgun-style UTXO notes, Poseidon hashing on BN254          | Railgun-fork privacy pool (Base) — same UTXO model adapted to Solidity                |
| Auth                | Ed25519 + Groth16 proof of spend authority                   | EIP-712 typed-data signatures                                                         |
| Composability       | Registered adapters (Jupiter, Kamino, Percolator, …)         | Whitelisted ERC-20s + integrated DEX swaps                                            |
| Replay protection   | Nullifier tree                                               | Random nonces + `validAfter` / `validBefore` windows                                  |

## Service Layer

The off-chain services that turn the protocol into a usable API.

**Facilitator** (EVM today) — verifies payment payloads, settles via the Relayer, handles smart-wallet UserOps, runs privacy-pool shield/transact/unshield. Live at `https://facilitatorv3.b402.ai`. See [Facilitator API](/developers/facilitator/overview).

**Hosted relayer** (Solana) — pays SOL for users, submits unshield / private-action transactions. See the [Solana SDK relayer page](/solana/sdk/scanner) and [Get-started flow](/solana/quickstart).

**b402scan** — agent reputation and seller discovery, multichain. See [b402scan](/b402-services/b402scan).

The Solana stack does not yet ship an HTTP-402 facilitator; that's on the roadmap.

## Developer Layer

Where you actually hook in.

- **SDK, Solana** → `@b402ai/solana` — see [installation](/solana/sdk/installation), [shield/unshield](/solana/sdk/shield-unshield), [private actions](/solana/sdk/private-actions).
- **SDK, EVM** → `@b402ai/sdk` — see [b402-sdk](/evm/sdks/b402-sdk), [agent-skill](/evm/sdks/agent-skill), [EIP-712 signature guide](/evm/sdks/eip712-signature-guide).
- **MCP server** — both stacks ship MCP tools so Claude/Cursor/agents can call payments and private actions directly. Solana side is documented in [Use it from an agent](/solana/mcp/overview).
- **Direct HTTP** — the Facilitator API is a plain JSON HTTP service; any client works.

## Privacy model in one paragraph

Both stacks implement the same idea: deposit a token into a shielded pool that records you as a commitment (a hash of your spending key, value, and salt), not as an address. When you spend, you publish a nullifier (derived from the commitment) and a zero-knowledge proof that some unspent commitment in the tree is yours, without revealing which. Adapters / DEX hooks let you bind that proof to a downstream action (swap, lend) inside the same transaction, so observers see a relayer doing a Jupiter swap, not you.

For the Solana threat model and what is *not* hidden, read [privacy model](/solana/concepts/privacy-model). For EVM, see [privacy-incognito](/evm/concepts/privacy-incognito).
